# ROBIN's Coffee website and editor: project spec

Nov 15, 2026 · @Harry

## 1. Overview

We rebuild robins-coffee.ch as a Hugo site in `github.com/harryf/robins-coffee`, improve its design, add events and a gallery, and then build a browser-based editor (a PWA) so non-technical people can change content through reviewed pull requests.

This spec is written to be executed with Claude Code on Harry's Mac. Each milestone in section 12 is a self-contained unit of work with acceptance criteria.

**Goals**

- A faster, better designed, mobile-first site that keeps ROBIN's identity and all current content.
- One events calendar that blends ROBIN's own Eventfrog events with IN YOUR FACE Comedy shows.
- A gallery and other content sourced from the venue's WhatsApp group export.
- A documented design system that the site and the editor both use.
- An editor PWA with GitHub login, live preview, pull requests and a self-update mechanism, shipped from the same repository.
- `main` is the only deploy branch and is protected; only named approvers can merge.

**Non-goals**

- No server-side CMS, database or paid hosting. The only server-side piece is one small login function (section 9).
- No ticket sales on the site. Tickets stay on Eventfrog.
- No native macOS app in this phase. The PWA replaces the earlier native app idea.

## 2. Stages

The project runs in four stages; each one ends with something deployable.

| Stage | Delivers | Done when |
| --- | --- | --- |
| 1. Clone and redesign | Hugo site with all current content, improved design, events calendar, gallery | Site is live on GitHub Pages and reviewed against the current site |
| 2. Design system | Tokens, components and a living style guide extracted from the stage 1 design | Every page is built only from documented components |
| 3. Editor PWA | Login, edit, preview, pull request, review, self-update | A non-technical editor publishes a change without touching GitHub's interface |
| 4. Handover | Protected `main`, approver list, editor guide, domain cut-over | robins-coffee.ch serves the new site |

Governance (section 11) is set up at the start of stage 1, so the workflow is in use before the editor exists.

## 4. Architecture

Everything lives in one public repository and deploys to GitHub Pages; the only moving part outside GitHub is a small login function.

&#91;embedded content: architecture · 6 parts\]

Editors never push to `main`. The editor opens pull requests, an approver merges, and GitHub Actions builds and publishes the site, the editor and a preview for every open pull request.

**Decisions**

- **Generator:** Hugo extended, version pinned in `.hugo-version` and used by both CI and local runs.
- **Hosting:** GitHub Pages, first at `harryf.github.io/robins-coffee/`, later on robins-coffee.ch. All links use Hugo's `relURL`/`absURL` so both the sub-path and the custom domain work.
- **Deploy:** an Actions workflow builds on every push to `main` and publishes to the `gh-pages` branch. `main` stays the single source of truth; `gh-pages` holds only build output.
- **PR previews:** the same workflow builds each pull request into `/pr-preview/pr-<number>/` on `gh-pages` and removes it when the PR closes.
- **Editor:** a separate front-end project in `editor/`, built by CI into `/edit/` of the published site, so merging to `main` ships editor updates.
- **No theme dependency:** layouts are written for this site, so the design system owns every component.

**Repository layout**

```
robins-coffee/
  .github/workflows/     deploy.yml, preview.yml, events.yml
  .github/CODEOWNERS     approvers
  .hugo-version
  hugo.toml
  content/               en/ and de/ page bundles
  data/                  hours.yml, site.yml, events/*.json, tokens.json
  layouts/               templates and partials (components)
  assets/                css, js, images processed by Hugo
  static/                files copied as-is
  editor/                PWA source (Vite + TypeScript)
  editor/schema.yml      content types and fields the editor shows
  scripts/               fetch_events.py, import_whatsapp.py
  docs/                  baseline/, design-system.md, editor-guide.md
  Makefile               serve, build, events, test
```

**Running locally (developers).** `make serve` runs `hugo server` with drafts and live reload on `localhost:1313`. Section 10 covers preview for non-technical editors.

## 5. Content model

All editable content is Markdown with front matter or a small YAML data file, so every change is a readable diff in a pull request.

| Type | Location | Key fields |
| --- | --- | --- |
| Page | `content/<lang>/<slug>/index.md` | title, description, hero image, body |
| Home sections | `content/<lang>/_index.md` | hero text, featured events count, featured gallery album |
| Manual event | `content/<lang>/events/<date>-<slug>/index.md` | title, start, end, doors, price text, ticket URL, image, category, body |
| Imported event | `data/events/eventfrog.json`, `data/events/iyf.json` | generated, never hand-edited (section 6) |
| Event override | `data/events/overrides.yml` | event id, hide, featured, replacement image or title |
| Gallery album | `content/<lang>/gallery/<album>/index.md` plus images in the bundle | title, date, cover, per-image alt text and caption |
| Menu | `data/menu.yml` | sections, items, price, dietary tags; names in EN and DE |
| Opening hours | `data/hours.yml` | regular hours per weekday, dated exceptions |
| Site settings | `data/site.yml` | address, phone, email, social links, announcement banner |

**Rules**

- English is the default language; German lives beside it with the same slugs. A missing translation falls back to English and is listed on an editor-only "untranslated" report.
- German text uses Swiss spelling.
- Images sit in page bundles so Hugo can resize them; originals are capped at 2400 px on the long edge before commit.
- `editor/schema.yml` describes each type's fields, labels, help text and validation. The editor builds its forms from this file, so adding a field is a pull request, not an editor release.
- Whether a Menu page is wanted is an open question (section 13); the model supports it either way.

## 6. Events

Events are fetched at build time into JSON data files and rendered as static HTML, so the site needs no API calls in the visitor's browser and no API key is ever exposed.

**Sources**

| Source | How | Notes |
| --- | --- | --- |
| Eventfrog | REST API at `api.eventfrog.net` with a read-only API key | Eventfrog offers a public key for public event data and organiser keys for an organiser's own events ([API keys](https://eventfrog.at/en/help/organizer/settings/api/api-keys.html), [integration options](https://eventfrog.at/en/help/organizer/settings/api/api-integration.html)) |
| IN YOUR FACE Comedy | A JSON feed published by inyourfacecomedy.ch | The calendar page could not be fetched while writing this spec. First task: check whether it exposes JSON-LD or a data file; if not, add `events.json` to that site's build |
| Manual | Markdown files in `content/<lang>/events/` | For events that are on neither platform |

**Pipeline (`scripts/fetch_events.py`)**

1. Fetch Eventfrog events for ROBIN's location and for the configured organiser ids.
2. Fetch the IN YOUR FACE Comedy feed and keep only events at ROBIN's.
3. Normalise both into one schema: `id`, `source`, `title`, `start`, `end`, `summary`, `image`, `ticket_url`, `category`, `organiser`.
4. De-duplicate. Comedy shows are sold on Eventfrog too, so the same show can arrive twice. Match on Eventfrog event id or ticket URL first, then on start time plus a normalised title. The IN YOUR FACE Comedy record wins for title, image and description; Eventfrog wins for ticket URL.
5. Apply `overrides.yml` (hide, feature, replace image).
6. Write the data files into the build workspace only. Imported events are never committed, so the nightly refresh needs no pull request and no exception to branch protection. Event images are downloaded and resized during the build.

**Schedule.** `events.yml` runs nightly, on demand from the Actions tab, and from a "Refresh events" button in the editor. The Eventfrog key lives in Actions secrets. The site is also rebuilt every morning so past events drop off without a content change.

**Display**

- Events page: upcoming events grouped by month, filter by category (comedy, music, other), each with date, time, image, short text and a ticket button.
- Home page: the next three to five events.
- Each IN YOUR FACE Comedy show carries a small brand label and links to its page on inyourfacecomedy.ch.
- Each event gets `Event` JSON-LD and an "add to calendar" `.ics` link; the full calendar is also published as one `.ics` feed.
- Each deploy also publishes the merged data as /events.json. If a fetch fails, the build reuses that last published file and the workflow reports the failure.

## 7. Gallery and WhatsApp import

The WhatsApp export is a private source that stays on Harry's Mac; only curated, cleaned images and text enter the public repository.

**Input.** A WhatsApp chat export (the `_chat.txt` file plus media) in a local folder outside the repo, for example `~/robins-whatsapp/`. The path is passed to the script as an argument and the folder name is in `.gitignore` as a safeguard.

**Import script (`scripts/import_whatsapp.py`)**

1. Parse the chat file into messages with date, sender and attachment name.
2. Build a local review page (`review.html`, not committed) with thumbnails grouped by day, plus nearby message text as context for captions and event announcements.
3. Harry ticks the photos to publish and assigns each to an album; the choice is saved to `selection.csv`.
4. For selected items only: strip all EXIF and location data, convert HEIC to JPEG, cap at 2400 px, rename to `<date>-<nn>.jpg`, and write them into gallery page bundles with draft alt text and captions.
5. Videos are skipped in the first pass and listed in a report.

**Privacy rules (the repo and its history are public)**

- No sender names, phone numbers or message text are committed unless Harry rewrites them as captions.
- Photos showing identifiable guests need the venue's agreement to publish; performers' promo shots are preferred. Anything doubtful stays out.
- Deleting a photo later does not remove it from git history without a history rewrite, so curation happens before commit, and PR previews are the last check.

**Gallery display**

- Album grid, then a responsive masonry grid per album, with a keyboard-accessible lightbox.
- Hugo generates WebP plus fallback at several widths, with lazy loading and fixed aspect-ratio boxes to avoid layout shift.
- Other content from the group (past event announcements, menu changes, opening-hour notices) is listed in the review page so it can be turned into events or pages by hand.

## 8. Design system

The design system is extracted from the approved stage 1 design and becomes the only way pages and the editor are styled.

**Tokens.** `data/tokens.json` is the single source. A Hugo template turns it into CSS custom properties, and the editor imports the same generated CSS.

| Group | Examples |
| --- | --- |
| Colour | brand, surface, text, accent, state colours; a light "day" and a dark "night" set |
| Typography | two families at most, self-hosted; a fluid type scale with `clamp()` |
| Space and layout | 4 px base scale, container widths, grid, breakpoints |
| Shape and depth | radii, borders, shadows |
| Motion | durations and easings, all disabled under `prefers-reduced-motion` |

**Components.** Each is one Hugo partial with documented parameters, plain CSS, and no JavaScript unless listed.

- Layout: header and nav, footer, section, grid, hero.
- Content: card, event card, event list, gallery grid, lightbox (JS), menu list, opening-hours table, map link, announcement banner.
- Controls: button, link, tag, filter chips (JS), language switch.
- Editor-only: form field, image picker, status badge, toast, dialog.

**Style guide.** A `/styleguide/` section of the site renders every token and every component with its variants and usage notes. It is built with the site, excluded from search engines, and is the visual regression reference.

**Rules**

- No hard-coded colours, sizes or fonts in layouts; only tokens.
- WCAG 2.2 AA contrast for every text and surface pair, checked in CI.
- Total CSS under 30 KB compressed; no CSS framework.
- A new component needs a style guide entry in the same pull request.
- `docs/design-system.md` records the principles, naming and the process for changes.

## 9. Editor PWA

The editor is an installable web app served from `/edit/` that hides git entirely: people sign in with GitHub, edit forms, see a preview and press "Submit for review".

**Stack**

- Vite, TypeScript and a small UI library (Preact or Svelte; Claude Code picks one and records why).
- GitHub REST API through Octokit; no git client in the browser.
- Rich text editing that reads and writes Markdown (TipTap or Milkdown), limited to the formatting the site supports.
- Styles from the design system tokens.
- UI in English and German.

**Login**

- A GitHub App installed only on `harryf/robins-coffee`, with repository permissions for contents, pull requests and metadata. This limits every user token to this one repository.
- GitHub's token endpoints cannot be called from browser code, for both the redirect flow and the device flow, so a backend step is required ([explanation](https://www.zonca.dev/posts/2025-01-29-github-auth-browser-device-flow)). A Cloudflare Worker of about 50 lines exchanges the login code for a token and refreshes it. It accepts requests only from the site's origins and stores nothing.
- The token is kept in memory with a refresh token in an origin-scoped store; "Sign out" clears both.
- Roles come from GitHub: write access means editor; being listed in `CODEOWNERS` or having admin access means approver. People without access see a "request access" screen with Harry's contact.

**Editing flow**

1. Dashboard: content by type, "My drafts" (my open pull requests), and for approvers "Waiting for review".
2. Open an item: a form generated from `editor/schema.yml`, with rich text for the body and a language toggle to edit EN and DE side by side.
3. Save draft: the editor creates a branch `edit/<login>/<slug>-<yyyymmdd>` from the latest `main`, commits all changed files in one commit through the Git Data API, and opens a draft pull request.
4. Preview (section 10).
5. Submit for review: the draft becomes a ready pull request with a plain-language summary of what changed.
6. Approver view: before and after, the preview link, then Approve and publish (approve plus squash merge) or Request changes with a comment.
7. After merge the editor shows "Published" once the deploy workflow finishes, and deletes the branch.

**Images.** Drag and drop or pick from the camera roll; the editor resizes to 2400 px, strips EXIF, requires alt text and commits the file into the page bundle.

**Guard rails**

- Validation from the schema (required fields, date order, URL format, image size) before a commit is allowed.
- Unsaved work is kept in IndexedDB, so a closed tab or lost connection loses nothing.
- If `main` changed the same file, the editor shows both versions and lets the editor reapply their change; it never force-pushes.
- Editors can touch only `content/`, `data/` (except generated event files) and images. A CI check fails any `edit/*` pull request that changes other paths.

**Self-update**

- Editor source lives in `editor/`; merging to `main` builds and publishes it with the site. That is the whole release process.
- The build writes `/edit/version.json` with version, commit and a `min_supported` version.
- A service worker caches the app shell with a cache name tied to the version. The app checks `version.json` on start, on focus and every 15 minutes.
- New version found: a banner offers "Update now"; accepting activates the waiting service worker and reloads after saving any draft. A version below `min_supported` must update before it can commit.
- An About screen shows the running version and commit, and a changelog generated from merged pull requests labelled `editor`.

## 10. Preview for editors

A PWA cannot start the Hugo program, because browsers do not let web apps run local binaries, so preview is delivered in three layers instead of one.

| Layer | What the editor sees | Speed | Fidelity | Needs |
| --- | --- | --- | --- | --- |
| A. Instant preview | The edited page, rendered inside the editor while typing | Immediate | Close, not exact | Nothing; works on phones |
| B. PR preview | The real Hugo build of their branch at `/pr-preview/pr-<n>/`, shown in the editor | About 1 to 2 minutes after saving | Exact | Nothing; works on phones |
| C. Local Hugo | The real site on `localhost:1313` with live reload | Immediate | Exact | A Mac with the helper installed, Chrome or Edge |

**A. Instant preview.** The editor renders Markdown and front matter through JavaScript versions of the main page templates (page, event, gallery album, menu, hours) using the design system CSS. It is labelled "Quick preview". Parity is kept honest by a CI test that compares its HTML with Hugo's output for sample content.

**B. PR preview.** Every saved draft triggers the preview workflow. The editor polls the workflow status, then loads the preview in a frame with phone, tablet and desktop widths. Approvers review this version. This is the default "real" preview and needs no installation.

**C. Local Hugo (optional, for power users).** A one-time installer puts the pinned Hugo binary and a tiny launcher on the Mac. The editor then:

1. asks for a local working folder through the File System Access API,
2. downloads the repository contents into it,
3. writes each edit to disk as the user types,
4. shows `localhost:1313` in the preview frame.

The launcher starts `hugo server` against that folder. Safari does not support the folder access this needs, so layer C is Chrome and Edge only.

**Spike, time-boxed to half a day.** Try compiling Hugo to WebAssembly so the exact build runs inside the PWA. There is no official browser build; a community fork compiles Hugo for WASI, which is a server-side target, not a browser ([hugo-wasm](https://git.deuxfleurs.fr/quentin/hugo-wasm/commit/eb25392c870d2fab75ca477b274e4dbab96413b0.diff)). If the spike works with acceptable size and speed, it replaces layer A and makes layer C unnecessary. If not, ship A and B first and C later.

## 11. Governance

`main` is protected so that every change arrives by pull request, passes the build and is approved by a named approver.

**Branch rules for `main`** (a repository ruleset; available on public repositories on the free plan, per [GitHub's documentation](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches))

- Require a pull request before merging, with 1 approval.
- Require review from Code Owners. `.github/CODEOWNERS` lists the approvers for `*`, so only their approval counts.
- Dismiss stale approvals when new commits are pushed.
- Require status checks: Hugo build, link check, editor path check, accessibility check.
- Block force pushes and branch deletion; squash merge only.
- Protect `gh-pages` too: only the Actions workflow writes to it.

**Roles**

| Role | Who | GitHub access | Can |
| --- | --- | --- | --- |
| Owner | Harry | Admin | Everything, including rules and secrets |
| Approver | Named in `CODEOWNERS` | Write | Approve and merge pull requests |
| Editor | Venue staff, comedians | Write | Create branches and pull requests through the editor |
| Visitor | Everyone else | None | Read the public site |

**Points to know**

- GitHub does not let authors approve their own pull requests, so at least two approvers are needed, or Harry's own changes wait for the second approver.
- On a personal repository every collaborator has write access; the rules above are what stop editors merging. Finer roles and bypass lists exist only for organisation-owned repositories ([GitHub docs](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)). If that is needed later, the repository can move to a free organisation.
- Because nothing can bypass the rules on a personal repository, no automation commits to `main`. Imported events are fetched at build time for this reason (section 6).
- Secrets (Eventfrog key, Worker credentials) live in Actions and Cloudflare secrets, never in the repository.
- Onboarding an editor: they create a GitHub account, Harry invites them as collaborator, they open `/edit/` and sign in. `docs/editor-guide.md` covers this in one page with screenshots.

## 13. Risks and open questions

The largest risks are permission to reuse the venue's content and the limits of preview inside a browser; both are handled early.

**Risks**

| Risk | Effect | Mitigation |
| --- | --- | --- |
| Content and brand belong to ROBIN's owners | A public clone without agreement could cause a dispute | Get written agreement before the repository goes public; keep it private or unlisted until then |
| Photos of guests from WhatsApp | Privacy complaints; history is hard to clean | Curation before commit, venue agreement, performer shots first (section 7) |
| Quick preview differs from the real build | Editors approve something that looks different live | Label it clearly; approvers always review the PR preview; parity test in CI |
| Eventfrog API access or limits | Empty or stale calendar | Last-good fallback, failure alerts, manual events as backup |
| Same show listed twice | Duplicate entries | Id and URL matching, title plus time fallback, unit tests with real samples |
| Editors without GitHub accounts | Slow onboarding | One-page guide; Harry sets accounts up in person |
| Only one approver available | Changes wait | At least two approvers from the start |
| Login function outage | Nobody can sign in | Worker is stateless and tiny; a signed-in session keeps working until its token expires |
