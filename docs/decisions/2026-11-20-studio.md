# The Studio: a Mac editor with a local preview

20 November 2026. Harry was not happy with the browser editor at `/edit/`: installed as an app it has no browser navigation, and its preview lives inside the editing screen. He asked for an editor that runs the site on a local web server, reloads it on every change, publishes with one button, shows a history, and takes events, albums, menu and pictures.

## What we chose

| Question | Choice | Why |
|---|---|---|
| Whose Mac | Harry's first, Elias's later (Harry) | The app needs bun, git and a copy of the site; packing that for a Mac without developer tools is a later step |
| The phone editor at `/edit/` | Stays | Small changes on the go |
| Publish | A pull request on an `edit/...` branch. For the owner it waits for the `build` check and merges itself; for anyone else it stops and waits for a yes (Harry) | The owner's click on Publish is the approval. Nobody pushes to `main` |
| Alt text | A draft from Apple Vision's labels and read words, finished by hand (Harry) | No key, no download, nothing leaves the Mac. The draft is a list, not a sentence |
| The cut of a picture | A focus point per photo in `focus.yml` | One file per photo stays the rule; the build cuts each shape around the point |
| An Eventfrog import | Becomes an ordinary event file with its source address | The build needs no key and does not depend on Eventfrog being up |
| Keys | macOS Keychain, service `robins-studio` | Not in a file that could be committed or backed up in the clear |
| The window | A small Swift program around a web view; the preview opens in the default browser | Harry wants real browser navigation for the preview |

## How the local server is kept shut

- It listens on 127.0.0.1 only.
- The editing screen is served from `127.0.0.1:<port>`, the preview from `localhost:<port>`. To a browser these are two origins, so a page of the built site cannot call the editing API.
- Every API request needs a token made new at each start, and the server's own Host and Origin.
- A write names no path of its own: the server builds it from a checked short name under a fixed folder, inside the edit scope.

## Known limits

- Not checked against GitHub yet: the owner's self merge through the API under the rule that asks for one approval. The first real publish will show it; if GitHub refuses, the screen says so and links the pull request.
- The Eventfrog list with a key is tested only against a made-up answer. Its shape is taken from the comedy site's client. The bar has no key yet.
- Neither poster for beer pong or chess prints a time, so those events show the day only.
- The app is not signed and has no icon. On another Mac, Gatekeeper will ask.
- A person who is not the owner stays on the `edit/...` branch after sending; nothing brings the folder back to `main` when someone else merges.
- The branch is cut from the folder's state. If `main` moved on GitHub in the same file, the merge is refused and nothing is rebased.
- The Studio works on the folder it is started from. Use a clone kept on `main`, not the folder where code is written.

## Second look (20 November 2026)

A read-only review of the server and the publish path before first use. It found no critical problem. What changed because of it:

| Finding | What we did |
|---|---|
| The preview also answered under the editing screen's own address, so a script in a page of the site could have read the screen's token | Fixed. The built site answers under `localhost` only, the screen under `127.0.0.1` only; the app window treats only `/_studio/` as its own |
| The start and end of an event were checked loosely and reached a file name and a line of YAML | Fixed. Exact times only, and the type of every field is checked first |
| A publish commit took everything that was staged | Fixed. The commit refuses anything staged outside the content folders |
| Eventfrog redirects were followed before the host was checked; pictures not checked after a redirect | Fixed. Redirects are walked by hand, each hop checked before it is asked |
| The raw file route wrote bytes as they came, metadata included; the scope let any file name into a content folder | Fixed. The route takes text for `.md` and `.yml` only. The scope names each folder's kind of file in lower case, so an original photo, a `.HEIC` or `TOKENS.JSON` never passes. The route itself stays, as the way to edit a text file that has no form yet |
| Saving a key may have read from the terminal when the Studio was started from one | Changed without proof of the fault: the key now goes to the keychain tool on its standard input as a command. A key may hold letters, digits and `_ . - = : + / ~ @ %` |
| Two Publish clicks could both start; discard paths were patterns; a token of odd bytes gave an error; the event stream had no origin check | Fixed |
| During a push the key is in the environment of the git process, which the same user can read | Accepted. Anything running as that user can ask the Keychain anyway |
| The app picks a free port, lets go of it and then starts the server on it | Accepted. Another program taking the port in between makes the start fail with a plain message |

Not looked at by the review: a running server or the built app, the site build, whether GitHub lets the owner's merge through, the shape of Eventfrog's API, how the picture library copes with a hostile file.

## Version, updates and the folder (20 November 2026)

Harry asked for a version number in the editor, a check for new versions at start with an automatic update, and a setting for the folder the editor works in.

| Question | Choice | Why |
|---|---|---|
| What a version is | A number in `src/studio/version.json`, shown with the commit | The Studio's code lives in the site's repository, so "newer" is a newer `main` |
| How it updates | At start, before the server's code is loaded: fetch `main` from the folder's own `origin`, fast-forward, install packages when they changed, rebuild the window program when it changed | No download server, no installer, nothing to sign. The same route works on Elias's Mac |
| When it does not | Not on `main`; GitHub out of reach; the folder holds commits GitHub lacks; the update changes a file with an unpublished change | The person's work always wins. The old version starts and Settings says why |
| Where the code may come from | Only the `origin` git has for the folder | `site.yml` is a content file. An address in it must never decide what code runs |
| The folder | Shown under Settings and changed there; kept in `~/Library/Application Support/ROBINs Studio/config.json`; used by the app from its next start | The app is one program, the folder is a choice. A folder is accepted only when it is a copy of the site with git and packages |

Known limits: a new window program is used from the second start after the update. An update that needs new packages while GitHub's package server is out of reach leaves new code with old packages; the Studio says so and names the command. The app is still unsigned.

## Screens, round two (20 November 2026)

Harry's rule for the screens: "don't make me think". Each one shows what is there first and puts the one thing to do next at the top.

| Screen | What changed |
|---|---|
| Photos | Albums and photos are one section. Pictures are shown album by album. No "use it as", no file name: the name comes from the caption, the day from the picture itself (its capture date, else the file's date) |
| Menu | Each drink shows its picture. One form to add or edit, with the picture upload inside it |
| Events | "Add an event" at the top, by hand or from Eventfrog. Each event shows its picture and its dates in words. A calendar of every upcoming event of the site at the bottom, read from the preview's own `events.json` |
| History | "Restore this version" brings the content files back to a commit as an unpublished change. It is refused while other unpublished changes exist. It moves no branch and commits nothing |
| Settings | Holds the tools list that used to be "This Mac" |

Since 0.9.2 (Harry's word): a picture the Studio made for a drink or an event (`photos/menu-*.jpg`, `photos/event-*.jpg`) is deleted when nothing names it any more, and an album can be renamed (its short name stays, so its photos stay in it). Still open: albums cannot be removed from the screen. A photo's day cannot be changed after it was added, since the day is part of its file name.

## Second look at the update, folder and restore code (20 November 2026)

It came back after the code was merged. One critical finding, four warnings.

| Finding | What we did |
|---|---|
| Critical: a page's `permalink` chose its output file with no limit, so a content change could make the build write outside its folder, on the Mac as well as in CI. With the self-update that could have broken the Studio or planted a file in the home folder | Fixed and reproduced first. A permalink may only name a plain `.html` file in lower case folders; the build checks again that every page lands inside its output folder |
| A link standing where a content file should be could carry a write or a restore somewhere else | Fixed. A link is taken away before the file is written; a test fails when anything under `site/` is a link |
| The phone editor's "yes" approved whatever the pull request held, also code | Fixed. Yes is offered only when every changed file is content and the list could be read whole |
| Rebuilding the app deleted the old one first; a failed install or rebuild was never tried again; the app gave up waiting too early | Fixed. The app is built beside the old one and swapped in; a failed step is tried again at the next start; the app waits nine minutes |
| The server took its GitHub address from `site.yml`, a content file | Fixed. The folder's own `origin` decides when it is on GitHub |
| An original photo could stay in the cache when a look was cut short | Fixed. Swept away at start |

Decided by Harry (20 November 2026): no rule on GitHub that a change outside the content folders needs the owner's review; the git history is enough for him. What that leaves: the edit-scope check in CI runs from the pull request's own copy of the workflow, so a person with write access could remove it in the same pull request. The phone editor no longer offers "yes" for such a change, which closes the blind route, not the deliberate one.

## Installing on another Mac, and the logo (21 November 2026)

Harry wants one link to give Elias, with instructions for adding the Studio to a laptop, and the bar's logo on the app.

| Question | Choice | Why |
|---|---|---|
| The link | A page of the site itself, `/studio/`, in English and German, kept out of search | It can explain every step in plain words and it moves with the site to its own domain |
| How it installs | One line pasted into Terminal runs `scripts/install-studio.sh` from `main` | The app is built on the person's own Mac, so macOS does not hold it back the way it holds back a downloaded app that is not signed. No Apple developer account is needed |
| What the script may do | Apple's tools and bun when missing, a clone in the Library folder, packages, the app in `~/Applications`. No password, no `sudo` | A person who is not a developer runs it; it must be safe to run again |
| Where things go | The copy of the site in `~/Library/Application Support/ROBINs Studio/site`, the app in `~/Applications`, both written to `config.json` | The copy is not for the person to open; the app is where apps are. The update rebuilds the app where it is |
| The logo | The roundel on the night colour as the app's icon, and beside the name in the sidebar | It is the bar's mark. It is a small bitmap until vector logos arrive, so the icon is a little soft at its largest sizes |

Known limits: the line asks a person to trust a script from the internet; the page says what it does and links its source. The Apple tools step can take ten minutes and needs a click in Apple's own window.
